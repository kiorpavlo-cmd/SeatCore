# Сервер Mio!

Настоящий локальный HTTP-сервер на Node.js 24+, с постоянной базой SQLite. Сторонние производственные зависимости не требуются. Сервер одновременно отдаёт сборку сайта из `../web/dist`.

## Запуск

```sh
npm start
npm run dev
npm test
npm run check
npm run backup
```

Адрес по умолчанию: http://127.0.0.1:4175. Настройки в `.env` необязательны; пример — `.env.example`. `DATABASE_PATH` и `WEB_DIST` разрешаются относительно папки server. `HOST` допускает только localhost: это текущая локальная версия без серверной авторизации.

## Что перенесено на сервер

Бронирования, лист ожидания, сотрудники, гости, теги, пользовательские поля, планы залов, блокировки, заметки, профиль ресторана, настройки прав, справочники и фоны хранятся в SQLite. База, окончательная проверка данных, атомарная запись, контроль версии, защита от повторного запроса, журнал действий и резервное копирование принадлежат серверу.

Браузер отвечает за представления и формы, предварительную проверку, личные фильтры и дату. При сохранении показывает состояние запроса: «Сохраняем…», «Сохранено» или ошибку. PIN новых пользователей записывается в базе как scrypt-хеш и исключается из ответов API. PIN и роли пока являются настройками, а не работающей авторизацией.

## Структура

- `src/http/` — маршруты API, разбор JSON и безопасная выдача статических файлов.
- `src/domain/` — проверка состояния и ошибки предметной области.
- `src/services/` — операции с состоянием, миграция, обработка PIN.
- `src/database/` — схема SQLite, транзакции, журнал и копии базы.
- `contracts/` — общие форматы и правила без браузерных или серверных зависимостей.
- `config/seed.json` — начальное состояние прежнего проекта.
- `scripts/` — резервное копирование и проверка синтаксиса.
- `tests/` — проверки SQLite, миграции, конфликтов, бизнес-правил и HTTP.

## Миграция и защита данных

При первом открытии на прежнем адресе браузер сохраняет исходный экспорт в `mio-browser-before-server-v1`. Если сервер ещё не инициализирован, прежние данные переносятся одним атомарным запросом с сохранением идентификаторов и старого журнала. Если сервер уже содержит данные, автоматическая замена запрещена; исходная браузерная копия остаётся доступной для экспорта в настройках. Данные с другого адреса автоматически недоступны браузеру: сначала экспортируйте их на прежнем адресе.

Каждая запись содержит текущую `baseRevision` и уникальный `mutationId`. Устаревшая версия получает 409; повтор того же запроса не создаёт дубль. При 409/422 браузер сохраняет черновик, загружает серверное состояние и показывает ошибку. При обрыве связи можно повторить запрос кнопкой состояния. После повторного открытия уже подключённого клиента без сервера запись приостанавливается: кеш остаётся доступным для просмотра. Черновик можно выгрузить в настройках. Несохранённый новый PIN не включается в черновик.

Не очищайте данные браузера до переноса и проверки резервной копии. Исходный экспорт браузера может содержать прежние данные, включая PIN, которые исходное приложение хранило открытым текстом.

## API

Ответы и ошибки — JSON. Мутации требуют `Content-Type: application/json`.

| Метод              | Адрес                        | Назначение                               |
| ------------------ | ---------------------------- | ---------------------------------------- |
| GET                | `/api/health`                | Проверка работы                          |
| GET                | `/api/v1/state`              | Состояние, версия и признак переноса     |
| PATCH              | `/api/v1/state`              | Атомарная запись нескольких коллекций    |
| POST               | `/api/v1/migrations/browser` | Однократный перенос старого localStorage |
| GET, POST          | `/api/v1/reservations`       | Бронирования                             |
| GET, PATCH, DELETE | `/api/v1/reservations/:id`   | Одна запись                              |

Такой же CRUD доступен для `waitlist`, `staff`, `guests`, `tags`, `tag-categories`, `custom-fields`. В GET списка поддержаны `q` и `date`. Бронирования без стола и лист ожидания сохраняются, как прежде; пересечения занятого стола и действующие ограничения проверяются сервером.

Пример PATCH состояния:

```json
{
  "baseRevision": 7,
  "mutationId": "unique-request-id",
  "changes": { "notes": { "2026-10-13": "Заметка" } }
}
```

`changes` содержит полное новое значение каждой указанной коллекции, поэтому нужно сначала прочитать актуальное состояние. Коллекции: `app`, `floor`, `blocked`, `blocks`, `notes`, `account`, `permissions`, `guests`, `fields`, `resources`, `backgrounds`. `app` включает бронирования, ожидание, сотрудников и названия залов. Поэлементные POST/PATCH используют `{baseRevision, mutationId, record}`; DELETE — `{baseRevision, mutationId}`. Ответ мутации — актуальное состояние.

## Копирование и восстановление базы

`npm run backup` создаёт SQLite-копию в `data/backups/` через API SQLite, согласованную с текущими данными. Можно указать путь: `npm run backup -- data/backups/manual.sqlite`. Существующий файл не перезаписывается. Каталог данных имеет права 700, база и копии — 600.

Для восстановления остановите сервер, сохраните отдельную копию текущего каталога data, укажите в `.env` `DATABASE_PATH=data/backups/manual.sqlite` и снова запустите сервер. Для дальнейшей работы можно использовать отдельную копию восстановленного файла. Не заменяйте работающую базу обычным копированием вместе с активными WAL-файлами.

## Дальнейшее расширение

Сейчас SQLite хранит проверяемые JSON-документы для совместимости с исходными данными, а версии, квитанции запросов и журнал — отдельные таблицы. Новые операции следует реализовывать в сервисах через транзакции и общую проверку; не обходить их прямой записью из HTTP-обработчика.

Для публичного SaaS отдельно нужны серверные сессии, полномочия, изоляция ресторанов, управление секретами и подключение провайдеров. Почта, SMS, WhatsApp, платежи и POS не отправляют внешние запросы в текущей версии. При росте нагрузки возможен переход к отдельным таблицам сущностей и PostgreSQL без переписывания страниц: клиент работает через адаптер API.
